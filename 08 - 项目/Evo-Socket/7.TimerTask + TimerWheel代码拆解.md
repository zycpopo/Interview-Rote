在高性能网络库中，**如何高效管理海量连接的超时剔除（如非活跃连接断开）** 是个关键问题
如果使用传统的 `std::priority_queue`（小顶堆）管理定时器，插入和删除的时间复杂度是 **$O(\log N)$**。当连接数达到数十万时，频繁的插入与刷新会导致显著的性能开销。

为了实现 **$O(1)$ 复杂度的定时任务添加、刷新的销毁**，网络库引入了**时间轮算法（Timing Wheel）**，并结合 Linux 专有的 **`timerfd`**，将其统一挂载到 `EventLoop` 的事件循环中。

## 一、TimerTask代码拆解

```c++
using TaskFunc = std::function<void()>;
using ReleaseFunc = std::function<void()>;
class TimerTask{
    private:
        uint64_t _id;       // 定时器任务对象ID
        uint32_t _timeout;  //定时任务的超时时间
        bool _canceled;     // false-表示没有被取消， true-表示被取消
        TaskFunc _task_cb;  //定时器对象要执行的定时任务
        ReleaseFunc _release; //用于删除TimerWheel中保存的定时器对象信息
    public:
        TimerTask(uint64_t id, uint32_t delay, const TaskFunc &cb):
            _id(id), _timeout(delay), _task_cb(cb), _canceled(false) {}
            
        ~TimerTask() {
            if (_canceled == false) _task_cb();
            _release();
        }
        void Cancel() { _canceled = true; }
        void SetRelease(const ReleaseFunc &cb) { _release = cb; }
        uint32_t DelayTime() { return _timeout; }
};
```
**原理**：`TimerTask` 通常由 `std::shared_ptr<TimerTask>` 管理。只要智能指针的引用计数归零，对象被析构，就会自动触发 `~TimerTask()`。如果任务被取消（`_canceled = true`），析构时就会静默销毁而不会触发业务回调。

为什么不直接用Connnection这个本身代表连接的类，而是用TimerTask挂进时间轮？
是为了避免循环应用，如果用Connection，会形成严重的内存泄漏。
遵循单一职责原则SRP，时间轮是通用的，与Connection直接解耦。
## 二、TimerWheel代码拆解
TimerWheel是时间轮盘容器，底层依赖Linux的timefd来提供精确的秒级心跳驱动。

### 1. **核心成员变量**：
```c++
class TimerWheel {
    private:
        using PtrTask = std::shared_ptr<TimerTask>;
        using WeakTask = std::weak_ptr<TimerTask>;

        int _tick;             // 当前时间轮指针指到的刻度（秒）
        int _capacity;         
        // 时间轮的最大容量（槽位数，例如 60 表示最多支持 60 秒超时）
        int _timerfd;          
        // Linux timerfd 文件描述符（用于产生内核每秒一次的读事件）
        EventLoop *_loop;      // 绑定的 EventLoop
        Channel _timer_channel;// 封装 _timerfd 的 Channel，挂载到 Poller 中

// 【时间轮轮盘】：vector 的每个元素是一个“槽”，槽里盛放着该秒内需要维持生命周期的任务
        std::vector<std::vector<PtrTask>> _wheel;
        
// 【任务索引表】：记录 conn_id -> WeakTask 的映射，用于 $O(1)$ 实现任务刷新和取消
        std::unordered_map<uint64_t, WeakTask> _timers;
};
```
- **`_wheel` 的数据结构**：它是一个**二维数组** `std::vector<std::vector<shared_ptr>>`。外层数组大小为 60，代表 60 个刻度槽；内层 `vector` 相当于一个容器，用来盛放“在这一秒内需要被维持生命”的所有 `TimerTask` 智能指针。
    
- **`_timers` 哈希表**：记录 `id -> weak_ptr`。为什么用 `weak_ptr`？因为如果用 `shared_ptr`，哈希表本身就会让任务的引用计数永远不为 0，导致任务永远无法析构（内存泄漏）。`weak_ptr` 只用于“查找”，不增加引用计数。

### 2. **核心实现原理与逻辑拆解**：
网络库并不用死循环去轮询时间。而是利用timerfd_create创建一个定时器fd，配置为每一秒触发一次可读事件。

#### 2.1 **内核驱动与心跳消费机制**
- **CreateTimerfd( )** 通过**timerfd_create**创建Linux定时器，并用**timerfd_settime**设置为：第一秒后第一次超时，之后每隔一秒就超时一次。
- **ReadTimerfd( )** 当timerfd可读时，读取出8个字节的整数times。
- **OnTime( )**拿到超时次数times后，通过for循环调用times次RunTimerTask( )；
- **RunTimerTask( )** 干两件事，第一个是`_tick = (_tick + 1) % _capacity;` 顺时针拨动秒针。第二步是：`_wheel[_tick].clear();` **【最核心的一步】**：清空该槽位中的所有 `shared_ptr`！
#### 2.2 **定时任务的**“增、刷新、删”
- **`TimerAddInLoop(id, delay, cb)`**：
	1. new出TimerTask，并通过bind给任务挂载一个析构清理回调RemoveTimer(id)。
	2. 计算放入哪个槽pos = (_tick + delay) % _capacity。
	3. 将shared_ptr塞进——wheel\[pos\],引用计数+1。
	4. 将weak_ptr记录在timers\[id\]索引表。
- **`TimerRefreshInLoop(id)`**：
	1. 在timers中通过id查找weak_ptr。
	2. 调用.lock( )将其提升为一个临时的shared_ptr。
	3. 重新计算新的目标槽位pos = (\_tisk +delay\)%\_capacity。
	4. 再次把这个shared_ptr压入_wheel\[pos]槽中。
- **`TimerCancelInLoop(id)`**：
		找到任务后调用pt->Cancel( ),把任务内部的_canceled标记置为true。后续哪怕指针被销毁，析构函数发现_canceled == true也不会触发业务回调。
## 三、设计精髓

### 1.利用C++RAII实现自动清除
- 无需像传统代码那样写 `if (now > timeout_time) { do_close(); }` 去轮询对比时间。只需把业务放入 `~TimerTask()` 析构函数中，**槽位一清空 $\rightarrow$ 指针归零 $\rightarrow$ 自动触发析构 $\rightarrow$ 执行死刑**。
### 2.O(1)时间复杂度延长存活时间
- 刷新连接超时（`TimerRefresh`）仅仅是往未来的数组槽位追加一次 `push_back`，极其高效。老槽位里的旧指针不用管，等秒针转过去自然会被清掉。
### 3.线程安全与无锁闭环：
- `_timerfd` 的读事件被封装在 `Channel` 里，挂载在 `EventLoop` 的 `Poller` 中。这意味着时间轮的转动（`OnTime`）、任务的添加（`TimerAdd`）和刷新（`TimerRefresh`）**全部串行运行在同一个 EventLoop 线程中**，完全不需要加锁！

## 四、场景模拟

#### 场景设定
- `_capacity = 60`（表盘共有 0 ~ 59 槽）。
- 当前 `_tick = 0`（秒针在 0 号槽）。
- 超时时间 `delay = 5` 秒（如果 5 秒没通信就关闭连接 `conn_1001`）。

#### 阶段一：新建连接，注册定时任务 (`TimerAddInLoop`)

1. **计算槽位**：`pos = (0 + 5) % 60 = 5`。
2. **压入槽位**：`_wheel[5].push_back(pt)`。
3. **此时状态**：
    - `5号槽` 里面持有了 `conn_1001` 任务的 `shared_ptr`
    - 引用计数 `use_count = 1`。

```Plaintext
  _tick = 0 (秒针)
    │
    ▼
  [ 0 ]   [ 1 ]   [ 2 ]   [ 3 ]   [ 4 ]   [ 5 ]  ... [ 59 ]
 (为空)  (为空)  (为空)  (为空)  (为空)   │
                                          └──► [ Task_1001 (RefCount: 1) ]
```

#### 阶段二：时间推移与数据通信 (重置心跳 `TimerRefreshInLoop`)

1. **第 1 秒到了**：内核唤醒 `timerfd` $\rightarrow$ 执行 `OnTime()` $\rightarrow$ `_tick` 变成 `1` $\rightarrow$ `_wheel[1].clear()`（1 号槽本身为空）。
2. **第 2 秒到了**：`_tick` 变成 `2`。
    - **【客户端发来数据了！】** `Connection::HandleRead` 被触发，立刻调用 `TimerRefresh(1001)`。
3. **刷新延迟**：
    - 算法重新计算目标槽位：`pos = (_tick + delay) % 60 = (2 + 5) % 60 = 7`。
    - 再次将 `pt` 压入 **`7号槽`** (`_wheel[7].push_back(pt)`)。
4. **此时状态**：
    - **`5号槽`** 存着一个 `shared_ptr`（最初加的）。
    - **`7号槽`** 也存着一个 `shared_ptr`（刚才刷新加的）。
    - 该任务的引用计数 `use_count` 变成了 **2**！

```Plaintext
                  _tick = 2 (秒针)
                    │
                    ▼
  [ 0 ]   [ 1 ]   [ 2 ]   [ 3 ]   [ 4 ]   [ 5 ]   [ 6 ]   [ 7 ]  ... [ 59 ]
                                            │               │
                                            │               └──► [ Task_1001]
                                            └──► [ Task_1001 ]
                                            (此时引用计数 = 2)
```

#### 阶段三：超时判定与优雅销毁

1. **第 5 秒到了**：`_tick` 移动到了 **`5号槽`**。
    - 执行 `_wheel[5].clear()`。
    - `5号槽` 内的 `shared_ptr` 被释放，引用计数从 **2 降为 1**。
    - **会触发超时断开吗？不会！** 因为 `7号槽` 还持有它，引用计数不为 0，`TimerTask` 的析构函数**不会运行**。连接继续存活！
2. **如果之后客户端再也不发数据了**：
    - 秒针继续走：第 6 秒（清空槽 6）、第 7 秒（秒针移到 **`7号槽`**）。
    - 执行 `_wheel[7].clear()`。
    - `7号槽` 内的 `shared_ptr` 被释放，引用计数从 **1 降为 0**！
    - **【关键时刻】** 引用计数归零，C++ 自动调用 `~TimerTask()`！
    - 析构函数内部触发 `_task_cb()`（即断开 Socket 连接），随后触发 `_release_cb()`（调用 `RemoveTimer(id)` 将自己从 `_timers` 哈希表中彻底抹除）。

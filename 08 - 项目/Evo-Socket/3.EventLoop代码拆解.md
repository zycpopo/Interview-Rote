- 在Reactor模式中，EventLoop事件循环是整个网络框架的心脏。
- EventLoop设计遵循One Loop Per Thread（一个线程一个事件循环）的思想。
## 一、代码拆解

### 1.核心成员变量
```c++
class EventLoop {
    private:
        std::thread::id _thread_id;          // 标识该 EventLoop 绑定的线程 ID
        int _event_fd;                  // Linux eventfd，用于跨线程唤醒 epoll
        std::unique_ptr<Channel> _event_channel; 
        // 专门管理 _event_fd 的Channel
        
        Poller _poller;               // 每个 Loop 独占一个 Poller(epoll 实例)
        std::vector<Functor> _tasks;         // 待执行的任务队列（任务池）
        std::mutex _mutex;                   // 保证任务队列线程安全的互斥锁
        TimerWheel _timer_wheel;             // 属于该 Loop 的时间轮定时器
};
```

### 2.核心函数与逻辑
1. **核心事件循环：**Start( )。这是EventLoop跑起来后的主循环，它的逻辑体现了经典的Reactor三步走设计模式：
```c++
void Start() {
    while(1) {
        // 1. 事件监控：调用 Poller 阻塞等待事件，获取活跃 Channel
        std::vector<Channel *> actives;
        _poller.Poll(&actives);

        // 2. 就绪事件处理：依次调用活跃 Channel 的事件处理回调
        for (auto &channel : actives) {
            channel->HandleEvent();
        }

        // 3. 执行异步任务：取出任务池中的任务并依次执行
        RunAllTask();
    }
}
```

2. **跨线程调度：**RunInLoop( )和QueueInLoop( )。网络库经常需要在EventLoop线程中执行某项操作，例如发送数据，修改监听事件等。为了避免多线程并发导致锁竞争和死锁问题，此框架采用“把任务投递给Loop所在线程去执行”。
```c++
// 判断任务是否在当前 Loop 线程中，是则直接调用，不是则放入任务池
void RunInLoop(const Functor &cb) {
    if (IsInLoop()) {
        return cb(); // 当前线程就是 Loop 线程，直接执行
    }
    return QueueInLoop(cb); // 其它线程调用的，存入任务池
}

// 将任务压入队列，并唤醒 Loop 线程
void QueueInLoop(const Functor &cb) {
    {
        std::unique_lock<std::mutex> _lock(_mutex);
        _tasks.push_back(cb); // 加锁写入任务队列
    }
    // 唤醒处于 epoll_wait 阻塞中的 Loop 线程
    WeakUpEventFd();
}
```

3. **跨线程唤醒：**`CreateEventFd()` / `ReadEventfd()` / `WeakUpEventFd()` ：如果EventLoop线程当前没有网络I/O事件，它就会阻塞在_poller.Poll( )，就是epoll_wait处。此时如果有其他线程通过QueueInLoop( ) 投递了任务，如何让该线程立刻醒来去处理任务。
   借助的是Linux专有的eventfd机制：
-  `CreateEventFd()`：创建一个非阻塞且随 `exec` 关闭的 `eventfd`。
- `WeakUpEventFd()`：其它线程向 `_event_fd` 写入一个 8 字节的 uint64_t 数据，立刻触发 `_event_fd` 的可读事件。
- `ReadEventfd()`：Loop 线程被唤醒后读取 `_event_fd` 里的内容，清除可读状态。
```c++
void WeakUpEventFd() {
    uint64_t val = 1;
    // 写入 8 字节数据，触发 _event_channel 的可读事件，使 epoll_wait 立即返回
    int ret = write(_event_fd, &val, sizeof(val));
    ...
}
```

4. **任务池消费：**RunAllTask( ):利用std::vector::swap实现高效无锁化消费；
```c++
void RunAllTask() {
    std::vector<Functor> functor;
    {
        std::unique_lock<std::mutex> _lock(_mutex);
        // 使用 swap 极短时间内把 _tasks 换出来，随后解锁
        // 这样在执行任务时，其它线程仍然可以向 _tasks 投递任务而不会被阻塞！
        _tasks.swap(functor);
    }
    for (auto &f : functor) {
        f(); // 依次执行所有的任务
    }
}
```

5. **代理通道和定时器操作：**`EventLoop` 还扮演了代理的角色，将 `Channel` 和 `TimerWheel` 的底层操作统一向上收拢：

- `UpdateEvent(Channel*)` / `RemoveEvent(Channel*)`：转发给 `_poller`。
- `TimerAdd()` / `TimerRefresh()` / `TimerCancel()`：转发给 `_timer_wheel`。

### 二、 EventLoop 在工作流程中的作用与原理

#### 1. 工作原理小结

`EventLoop` 的实现原理可以概括为：**“多路复用 + eventfd 唤醒 + 任务队列”** 的三合一驱动模型。

Plaintext

```
               +----------------------------------+
               |        EventLoop::Start()        |
               +----------------------------------+
                                |
                                v
               +----------------------------------+
               |       1. Poller::Poll()          | <--- 阻塞等待 I/O 事件 / eventfd 唤醒
               +----------------------------------+
                                |
                                v
               +----------------------------------+
               |    2. Channel::HandleEvent()     | ---> 触发 Socket 读写回调 / Timer 读回调 / eventfd 读回调
               +----------------------------------+
                                |
                                v
               +----------------------------------+
               |       3. RunAllTask()            | ---> 消费 QueueInLoop 压入的跨线程任务
               +----------------------------------+
                                |
                                +--- (循环往复)
```

#### 2. 在实际工作流程中的四大作用

##### 作用一：作为驱动整个 Loop 线程运行的引擎

每个工作线程中都会运行一个 `EventLoop::Start()`，它死循环式地死守在 `epoll_wait` 处，一旦有网卡数据到、定时器超时或其它线程唤醒，它就立即跑起来分派任务，没有事件时就挂起让出 CPU。

##### 作用二：实现跨线程调度的“无锁化/串行化”安全机制

在多线程网络编程中，如果 **线程A** 想直接修改 **线程B** 上的 `Connection`（例如跨线程发送数据或关闭连接），容易引发严重的竞态条件（Race Condition）。

`EventLoop` 解决此问题的机制是：

1. **线程A** 调用 `conn->Send(data)` ；
    
2. `Send()` 内部调用 `_loop->RunInLoop(...)` ；
    
3. `RunInLoop` 发现当前不是 Loop 线程，于是把发送任务 `SendInLoop` 封装成 lambda 放入 `_tasks` 队列，并写 `eventfd` 唤醒 Loop 线程；
    
4. Loop 线程醒来，在 `RunAllTask()` 中**由 Loop 线程自己去执行发送操作**。
    

> **结论**：所有对该套接字的操作都被收拢到同一个线程内串行执行，避免了在 `Connection` 内部频繁加锁。

##### 作用三：解决 `epoll_wait` 的死锁/假死阻塞（eventfd 唤醒）

如果没有 `eventfd`，当 Loop 线程处理完当前轮次的网络事件后，就会再次沉睡在 `epoll_wait` 中。此时如果其它线程往任务队列投递了任务，如果**没有网络事件触发**，这个任务就永远得不到执行。

`eventfd` 保证了：**一旦任务队列有了新任务，Loop 线程能被“瞬间叫醒”并立即处理任务。**

##### 作用四：集成统一的定时器调度

`TimerWheel` 底层使用的 `timerfd` 本质上也是一个文件描述符。`EventLoop` 将 `timerfd` 的读事件交由 `Poller` 一起监控（即 `_timer_channel`）。

- 内核超时 $\rightarrow$ `timerfd` 可读 $\rightarrow$ `Poller` 被唤醒 $\rightarrow$ 触发 `TimerWheel::OnTime()` $\rightarrow$ 时间轮转动，触发超时销毁逻辑。
    

这种把**网络 I/O 事件**和**定时器事件**统一在同一个 `epoll` 中监控的做法，是现代高性能网络库的标准设计方案。

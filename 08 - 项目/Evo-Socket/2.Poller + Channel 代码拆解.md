在基于 Reactor 模式的网络库中，`Poller` 和 `Channel` 是**事件驱动机制的基石**：

- **`Channel`** 负责**事件的封装与分发**（它知道某个 fd 关心什么事件，以及事件就绪后该调用哪个回调）。
- **`Poller`** 负责**事件的监听与收集**（它对 Linux 的 `epoll` 进行封装，负责向内核注册、修改、删除事件，并在 `epoll_wait` 就绪时告知上层）。

下面对这两个类的代码结构、逻辑关系以及实际工作流程进行详细拆解。

### 一、 代码拆解

#### 1. `Channel` 类拆解

`Channel` 充当了文件描述符 `fd` 与 `EventLoop` / `Poller` 之间的**中介**。

- **核心成员变量：**

    - `int _fd`：管理的套接字/文件描述符。
    - `EventLoop *_loop`：该 Channel 所属的事件循环对象。
    - `uint32_t _events`：**用户希望监控的事件**（如 `EPOLLIN` 读事件、`EPOLLOUT` 写事件）。
    - `uint32_t _revents`：**内核实际触发/就绪的事件**（由 `Poller` 在监听到事件后填入）。
    - `EventCallback _read_callback / _write_callback / _error_callback / _close_callback / _event_callback`：各类事件触发时的业务回调函数。
    
- **核心方法分类：**

    1. **事件状态修改：**
        - `EnableRead()` / `DisableRead()`：开启/关闭读事件监控（设置 `_events |= EPOLLIN` 并调用 `Update()`）。
        - `EnableWrite()` / `DisableWrite()`：开启/关闭写事件监控（设置 `_events |= EPOLLOUT` 并调用 `Update()`）。
        - `DisableAll()`：取消所有事件监控。

    2. **与 Poller 的交互：**
    
        - `Update()`：最终调用 `_loop->UpdateEvent(this)`，进而触发 `Poller::UpdateEvent()` 将事件更新到内核。
        - `Remove()`：将该 Channel 从 `Poller` 中彻底移除。

    3. **事件处理核心 `HandleEvent()`：**

```c++
    void HandleEvent() {
        // 1. 读事件 / 对端半关闭 / 带外数据
        if ((_revents & EPOLLIN) || (_revents & EPOLLRDHUP) || (_revents & EPOLLPRI)) {
            if (_read_callback) _read_callback();
        }
        // 2. 写事件
        if (_revents & EPOLLOUT) {
            if (_write_callback) _write_callback();
        }
        // 3. 错误事件
	    else if (_revents & EPOLLERR) {
            if (_error_callback) _error_callback();
        }
        // 4. 挂断事件
        else if (_revents & EPOLLHUP) {
            if (_close_callback) _close_callback();
        }
        // 5. 任意事件回调（通常用于刷新连接活跃度/定时器）
        if (_event_callback) _event_callback();
    }
```
        
#### 2. `Poller` 类拆解

`Poller` 是对 Linux 原生 `epoll` 系统调用的直接封装，负责执行真正的 I/O 多路复用。

- **核心成员变量：**

    - `int _epfd`：由 `epoll_create` 创建的 epoll 句柄。
    - `struct epoll_event _evs[MAX_EPOLLEVENTS]`：用于接收 `epoll_wait` 返回的就绪事件数组。
    - `std::unordered_map<int, Channel *> _channels`：维护 `fd` 到 `Channel*` 的映射表，方便通过就绪的 `fd` 快速定位到对应的 `Channel` 对象。
    
- **核心方法分类：**

    1. **内部私有操作 `Update(Channel *channel, int op)`：**
    
        封装 `epoll_ctl`，将 `channel->Fd()` 和 `channel->Events()` 打包成 `struct epoll_event` 提交给内核。
        
    1. **事件更新/添加 `UpdateEvent(Channel *channel)`：**
        
        检查 `_channels` 中是否存在该 fd： 
        - **不存在**：插入映射表，并执行 `epoll_ctl(..., EPOLL_CTL_ADD, ...)`。
        - **存在**：执行 `epoll_ctl(..., EPOLL_CTL_MOD, ...)`。

    1. **事件移除 `RemoveEvent(Channel *channel)`：**

        从 `_channels` 中删除该映射，并执行 `epoll_ctl(..., EPOLL_CTL_DEL, ...)`。
    
    2. **事件等待与收集 `Poll(std::vector<Channel*> *active)`：**
        
```c++
    void Poll(std::vector<Channel*> *active) {
         // 阻塞等待事件发生
        int nfds = epoll_wait(_epfd, _evs, MAX_EPOLLEVENTS, -1);
        // ... 错误处理 ...
        for (int i = 0; i < nfds; i++) {
            auto it = _channels.find(_evs[i].data.fd);
            assert(it != _channels.end());
            // 将内核返回的就绪事件设置到对应的 Channel 中
            it->second->SetREvents(_evs[i].events);
            // 将就绪的 Channel 放入活跃列表中
            active->push_back(it->second);
        }
    }
```
        
### 二、 Poller 与 Channel 的关系逻辑

1. **一对多关系**：一个 `EventLoop` 包含一个 `Poller`，而一个 `Poller` 可以同时管理多个 `Channel`（通过 `_channels` 哈希表）。

2. **面向对象解耦**：`Poller` 只关注 Linux 底层的 `fd` 和 `epoll_event`，不关心具体的业务逻辑；`Channel` 绑定了具体的业务回调（如读/写/错误），将底层事件转化为了 C++ 函数回调。

3. **数据流向闭环**：

    - **下发（设置监听）**：用户/上层代码 $\rightarrow$ `Channel::EnableRead()` $\rightarrow$ `EventLoop::UpdateEvent()` $\rightarrow$ `Poller::UpdateEvent()` $\rightarrow$ `epoll_ctl` 内核注册。
        
    - **上报（处理事件）**：内核通知 $\rightarrow$ `epoll_wait` $\rightarrow$ `Poller::Poll()` 收集活跃 Channel 并填充 `_revents` $\rightarrow$ `EventLoop` 遍历活跃 Channel $\rightarrow$ `Channel::HandleEvent()` 触发业务回调。

### 三、 实际工作流程（以连接有数据可读为例）

假设当前已经建立了一个 TCP 连接，套接字文件描述符为 `connfd = 5`。
#### 阶段 1：初始化与注册监听

1. **创建 Connection**：`TcpServer` 收到新连接，创建 `Connection` 对象，分配其专属的 `Channel`（内部包含 `connfd`）。
2. **设置回调**：`Connection` 给 `Channel` 设置读回调 `HandleRead()`。
3. **开启监听**：`Connection` 调用 `Established()`，触发 `_channel.EnableRead()`。
4. **状态流转**：
    - `Channel::EnableRead()` 将 `_events` 加上 `EPOLLIN` 标志。
    - 调用 `Channel::Update()` $\rightarrow$ `EventLoop::UpdateEvent()` $\rightarrow$ `Poller::UpdateEvent()`。
    - `Poller` 发现 `connfd` 不在 `_channels` 中，将其加入映射，并调用 `epoll_ctl(_epfd, EPOLL_CTL_ADD, connfd, &ev)`。
    - **此时内核开始监听 `connfd` 的可读事件。**

#### 阶段 2：事件发生与等待（Poller 工作）

1. 客户端发送了一段数据，Linux 内核网卡驱动接收并拷贝到 Socket 接收缓冲区，`connfd` 变为**可读状态**。
2. `EventLoop::Start()` 在主循环中调用 `_poller.Poll(&actives)`。
3. `Poller` 内部的 `epoll_wait` 被唤醒，返回 `nfds = 1`，`_evs[0]` 中包含了 `connfd` 及其就绪事件 `EPOLLIN`。
4. `Poller` 在 `_channels` 中根据 `connfd` 查找到对应的 `Channel*`。
5. 调用 `channel->SetREvents(EPOLLIN)`，将就绪事件存入 Channel 的 `_revents`。
6. 将该 `Channel*` 追加到 `actives` 数组中。

#### 阶段 3：事件分发与处理（Channel 工作）

1. `Poller::Poll()` 执行完毕返回，`EventLoop` 获取到了包含活跃 Channel 的 `actives` 列表。
2. `EventLoop` 遍历 `actives`，调用 `channel->HandleEvent()`。
3. `Channel::HandleEvent()` 检查自身的 `_revents`：
    - 识别出 `_revents & EPOLLIN` 为真。
    - 触发之前绑定的 `_read_callback()`（即 `Connection::HandleRead()`）。
4. `Connection::HandleRead()` 被执行，从 `connfd` 中读取数据到输入缓冲区 `_in_buffer`，并继续向上传递给用户的业务逻辑。

#### 阶段 4：取消监听/销毁

1. 当连接需要关闭或不再关心写事件时（例如发送缓冲区已清空），`Channel` 会调用 `DisableWrite()` 或 `Remove()`。
2. `Channel::Remove()` $\rightarrow$ `EventLoop::RemoveEvent()` $\rightarrow$ `Poller::RemoveEvent()`。
3. `Poller` 调用 `epoll_ctl(_epfd, EPOLL_CTL_DEL, connfd, NULL)`，并从 `_channels` 哈希表中抹除该节点，完成清理。

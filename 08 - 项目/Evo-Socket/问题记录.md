## Day 1 · 任务 1：架构全景（3 题）

**1. 为什么主线程只 accept，不处理读写？**
accept 是极轻量操作（一次系统调用），如果主线程还处理读写，accept 会被阻塞，新连接建立延迟。单独拎出来，保证新连接建立速度。

**2. 为什么每个工作线程独立跑一个 EventLoop，而不是共享一个？**
共享 EventLoop 意味着多个线程操作同一个 epoll 实例和同一个任务队列，必须加锁，锁竞争会成为瓶颈。每个线程独立 EventLoop = **线程封闭**（thread confinement），连接分配给哪个线程就永远归哪个线程管，全程无锁。

**3. 为什么需要 eventfd？**
工作线程可能正阻塞在 `epoll_wait` 里。这时主线程（或其他线程）要给这个连接投递一个任务（比如 Send 数据），怎么让它从 epoll_wait 里醒过来？答案是给这个 EventLoop 的 eventfd 写一个字节——eventfd 也是一个被 epoll 监听的 fd，写了数据就触发可读事件，epoll_wait 立刻返回，然后执行任务池的任务。

## Day 1 · 任务 2：Poller + Channel（5 题）

**1. `_events` 和 `_revents` 有什么区别？**
`_events` 是"想监控的事件"，通过 `epoll_ctl` 注册给内核；`_revents` 是"实际就绪的事件"，由 `epoll_wait` 返回后经 `SetREvents` 回填。两者分开是因为你关心的事件和这次实际发生的事件不一定相同（比如同时关注读写，这次只就绪读）。

**2. Channel 的职责是什么？为什么不直接在 Poller 里处理事件？**
Channel 封装"一个 fd + 关注的事件 + 5 个回调"，是 fd 的代言人；Poller 只管 epoll 系统调用和 fd→Channel 映射，不关心事件怎么处理。解耦后，把底层从 epoll 换成别的 IO 复用只需改 Poller，Channel 和上层不动。

**3. HandleEvent 里 EPOLLRDHUP 为什么和 EPOLLIN 放一起？**
EPOLLRDHUP 表示对端关闭了写半连接，此时本端可能还有数据没读完。先触发读回调把剩余数据读完再处理关闭，避免数据丢失。

**4. HandleEvent 里 write/error/hup 为什么用 else if，而不是独立 if？**
这三类事件都可能释放连接，一次只处理一个，避免在写回调执行时连接已被错误回调释放，造成野指针。

**5. Channel::Update/Remove 为什么实现在 event_loop.hpp，而不是 channel.hpp？**
Update 内部要调 EventLoop 的方法，而 event_loop.hpp 已经 include 了 channel.hpp，若在 channel.hpp 实现就会循环依赖。所以 channel.hpp 只做前向声明，实现放到 event_loop.hpp。

## Day 1 · 任务 3：EventLoop（8 题）

**1. EventLoop 的三步循环是什么？为什么是这个顺序？**
`Poll()` 阻塞等就绪 → `HandleEvent()` 处理就绪事件 → `RunAllTask()` 执行任务池。IO 事件优先处理（有时效性），跨线程投递的任务放最后，避免一个耗时任务推迟所有 IO 响应。

**2. RunInLoop 和 QueueInLoop 有什么区别？**
RunInLoop 先判断当前线程是否就是 loop 线程：是就直接执行 cb，否则才调 QueueInLoop；QueueInLoop 负责加锁把任务压入 `_tasks`，再 `WeakUpEventFd` 唤醒。

**3. RunAllTask 为什么用 swap，而不是持锁遍历 _tasks？**
任务执行可能很耗时，甚至再触发投递。先在临界区里 `swap` 把任务瞬间倒到局部 vector 就释放锁，执行阶段不持锁，临界区最短，其他线程 QueueInLoop 不会被阻塞。

**4. eventfd 为什么设 EFD_NONBLOCK 和 EFD_CLOEXEC？**
NONBLOCK：ReadEventfd 只是读走信号，无数据（EAGAIN）时必须立即返回，不能阻塞，否则整个 EventLoop 卡死；CLOEXEC：fork 后子进程 exec 时自动关闭，防止 fd 泄漏。

**5. EventLoop 如何保证对 Connection 的操作线程安全？**
靠线程封闭：Connection 的所有操作（Send/Shutdown/Established 等）都经 RunInLoop，实际执行被串行化到它唯一所属的 EventLoop 线程，全程无需加锁。

**6. EventLoop 和线程是什么对应关系？IsInLoop / AssertInLoop 干什么？**
严格一对一：一个线程只跑一个 EventLoop，构造时用 `_thread_id` 记录。IsInLoop 判断当前线程是否为所属线程；AssertInLoop 断言必须在 loop 线程（如 Upgrade 协议切换要求立即在本线程执行）。

**7.（深度）在 EventLoop 自己线程里调 QueueInLoop，还需要唤醒吗？**
从执行流看，本线程内入队的任务会在紧接着的 RunAllTask 被执行，唤醒并非必需；但代码无条件 WeakUpEventFd，是为了逻辑统一、不依赖"调用方精确判断自己是否即将阻塞"，写 eventfd 代价极小，且能覆盖恰好在进入 Poll 边界的情况。

**8.（健壮性）RunAllTask 里某个任务抛异常会怎样？**
代码没有 try/catch，异常会向上抛出 Start 的 while 循环，导致该 EventLoop 线程退出。这是一个可改进点（可在循环内捕获、记录日志后继续），面试时主动提出能体现工程意识。

## Day 1 · 任务 4：Connection 状态机（8 题）

**1. Connection 的四状态机是什么？怎么迁移？**
DISCONNECTED（已释放）/ CONNECTING（刚创建待就绪）/ CONNECTED（正常通信）/ DISCONNECTING（半关闭）。路径：CONNECTING →（EstablishedInLoop）→ CONNECTED →（ShutdownInLoop）→ DISCONNECTING →（ReleaseInLoop）→ DISCONNECTED。

**2. Send 为什么不直接 write，而要拷贝进 out_buffer？**
三个原因：① Send 可能被其他线程调用，直接操作 fd 有竞态；② 非阻塞 socket 可能写不完（EAGAIN），剩余数据要缓冲；③ 传入的 data 可能是临时空间，任务延迟执行时已释放，先拷贝进局部 Buffer 才安全。

**3. HandleWrite 发完后为什么 DisableWrite？**
LT 水平触发下，只要发送缓冲区可写，epoll 就一直返回 EPOLLOUT，发完还关注可写会造成忙等（CPU 100%）。所以发完立即 DisableWrite，有新数据再 EnableWrite。

**4. Shutdown 和 Release 有什么区别？**
Shutdown 只是把状态置为 DISCONNECTING（半关闭），先处理完 in_buffer、等 out_buffer 发完才真正关闭；Release（ReleaseInLoop）才是实际释放。这样保证关闭时不丢数据。

**5. ReleaseInLoop 的五步顺序？为什么先调用户回调再从 _conns 移除？**
顺序：状态置 DISCONNECTED → Channel.Remove（移出epoll）→ Socket.Close（关fd）→ 取消定时器 → 调用户 closed_callback → 调 server_closed_callback 移除服务器连接。必须先回调再移除：若先从 _conns 移除，shared_ptr 引用可能归零导致对象析构，再回调就是野指针。

**6. 为什么 Connection 要继承 enable_shared_from_this？**
Connection 由 shared_ptr 管理，回调中需要安全持有自身。shared_from_this() 返回指向自身的 shared_ptr，保证回调执行期间对象不被释放；裸 this 无法延长生命周期。

**7. 非活跃连接释放的完整链路？**
EnableInactiveRelease(sec) → TimerAdd(conn_id, sec, Release)；每次 HandleEvent（任意事件）TimerRefresh 续命；sec 秒无事件 → 时间轮到期 → Release。

**8. HandleRead 如何识别对端关闭？**
Socket::Recv 把 recv 返回 0（对端正常关闭）和真正错误统一转成 -1（EAGAIN/EINTR 转 0）。HandleRead 收到 -1 就调 ShutdownInLoop 进入关闭流程；返回正数才是收到数据。

## Day 2 · 任务 1：TcpServer + Acceptor（4 题）

**1. TcpServer::Start() 为什么先 _pool.Create() 再 _baseloop.Start()？**
_baseloop.Start() 是阻塞死循环，一旦执行就不会返回，所以必须先把工作线程池 Create 起来，最后才让主线程进入循环；顺序反了，工作线程永远创建不了。

**2. 连接表 _conns 为什么不需要加锁？**
它的两类操作都封闭在主线程（baseloop）：insert 在 NewConnection（accept 回调，主线程），erase 在 RemoveConnection（通过 _baseloop.RunInLoop 投递，也在主线程执行）。只有一个线程访问，天然无锁。

**3. RemoveConnection 为什么要通过 _baseloop.RunInLoop，而不是直接 erase？**
连接的实际释放 ReleaseInLoop 发生在工作线程，若在那里直接 erase 主线程的 _conns 就跨线程并发了。投递回 baseloop 执行，保证 _conns 的线程封闭。

**4. Acceptor 为什么必须先 SetAcceptCallback 再 Listen？**
启动读事件监控后可能立即有连接到达，如果处理新连接的回调还没设置，新连接得不到处理且 fd 泄漏。所以严格"先注册回调、后启动监听"。

## Day 2 · 任务 2：ThreadPool（3 题）

**1. EventLoop 为什么必须在工作线程内创建，而不是主线程建好传进去？**
EventLoop 构造时用 `_thread_id = std::this_thread::get_id()` 绑定当前线程，后续 IsInLoop 判断都依赖它。在主线程创建会让它误以为自己属于主线程，线程封闭就失效了。

**2. LoopThread::GetLoop 为什么要用条件变量等待？**
构造时只是启动了线程，线程调度有延迟，线程入口里的 EventLoop 可能还没建好、_loop 还是 NULL。条件变量 + 谓词 `_loop != NULL` 保证建好才返回，同时防止虚假唤醒。

**3. NextLoop 的分配策略？SetThreadCount(0) 时是什么模式？**
正常用 round-robin 轮询，让连接均匀分摊；count=0 时不创建工作线程，NextLoop 直接返回 baseloop，即单 Reactor 模式，连接全在主线程处理。

## Day 2 · 任务 3：Timer 时间轮（5 题）

**1. 时间轮是怎么工作的？timerfd 起什么作用？**
60 个槽组成环形数组，timerfd 设置为每 1 秒超时一次并注册到 EventLoop；每次超时秒针走一格，clear 对应槽，槽内任务的 shared_ptr 被释放、析构并执行。

**2. TimerTask 为什么"析构时才执行任务"？**
用 shared_ptr 的生命周期来管理任务到期：槽没被 clear，任务就活着；槽 clear 后引用计数归零、对象析构，在析构函数里执行回调。这样"任务到期"和"对象析构"天然绑定，无需手动判断。

**3. _timers 为什么用 weak_ptr 而不是 shared_ptr？**
_timers 只用于按 id 查找任务（Refresh/Cancel），weak_ptr 不增加引用计数，不会因为映射表存在而延长任务寿命；若用 shared_ptr，任务即使从轮上移除也会被映射表一直持有，无法释放。

**4. TimerRefresh 是怎么"续命"的？**
通过 weak_ptr.lock() 拿到任务的 shared_ptr，重新挂到 (_tick+delay) 秒后的新槽。旧槽到期 clear 时，新槽还持有一份，引用计数 ≥1 不会析构，任务被延迟。

**5. 时间轮和最小堆对比，为什么选时间轮？**
时间轮添加、取消都是 O(1)；最小堆添加 O(log n)、取消需先查找 O(n)。本项目大量连接超时都是短周期任务，时间轮更合适。固定 60 槽也意味着最大延迟为 60 秒。

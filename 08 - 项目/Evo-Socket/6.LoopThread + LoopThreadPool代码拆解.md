普通线程池是一堆线程抢任务；这里的LoopThreadPool是预先创建N个线程，然后线程内部固定有一个EventLoop，每个线程LoopThread管理这个指针，TcpServer在创建新连接时会在这里面进行挑选。

`LoopThread` 负责**创建并管理单个子线程及其 EventLoop**，而 `LoopThreadPool` 则负责**统筹管理这些线程，并按轮询策略分发连接**。
## 一、LoopThread：一个线程+一个EventLoop
```c++
class LoopThread {
    mutex _mutex;
    condition_variable _cond;
    EventLoop *_loop;      // 在线程内创建
    std::thread _thread;

    void ThreadEntry() {              // 线程入口
        EventLoop loop;               // ★ EventLoop 在【线程内】创建
        {
            unique_lock<mutex> lock(_mutex);
            _loop = &loop;
            _cond.notify_all();       // 通知 GetLoop：我建好了
        }
        loop.Start();                 // 进入事件循环（阻塞）
    }
public:
    LoopThread() : _loop(NULL),
        _thread(std::thread(&LoopThread::ThreadEntry, this)) {}

    EventLoop *GetLoop() {
        unique_lock<mutex> lock(_mutex);
        _cond.wait(lock, [&](){ return _loop != NULL; }); // 没建好就等
        return _loop;
    }
};
```

- **局部栈对象的生命周期绑定**：`EventLoop loop;` 是定义在 `ThreadEntry()` 函数内部的局部变量。由于 `loop.Start()` 是一个死循环，只要子线程不退出，`loop` 对象在栈上的内存就**绝对不会被释放**。
    
- **避免条件竞争（Race Condition）**：主线程在调用 `LoopThread` 创建线程后，如果立刻去拿 `_loop` 指针，子线程可能还没来得及执行构造函数。使用 **`std::mutex` + `std::condition_variable`** 完美解决了初始化先后顺序的问题。
## 二、LoopThreadPool：管理 N 个 LoopThread
`LoopThreadPool` 是从属 Reactor 线程池，它管理着多个 `LoopThread`，并暴露 `NextLoop()` 接口供主 Reactor 挑选子线程。
```c++
void Create() {
    if (_thread_count > 0) {
        _threads.resize(_thread_count);
        _loops.resize(_thread_count);
        for (int i = 0; i < _thread_count; i++) {
            _threads[i] = new LoopThread();
            _loops[i] = _threads[i]->GetLoop();  // 阻塞直到拿到 loop
        }
    }
}

EventLoop *NextLoop() {
	// 单线程模式兜底：如果没有开启子线程池，直接返回主 Reactor (_baseloop)
    if (_thread_count == 0) return _baseloop;    // 单线程模式：用主 loop
    // 负载均衡：使用 Round-Robin 轮询算法，依次分发连接
    _next_idx = (_next_idx + 1) % _thread_count; // round-robin
    return _loops[_next_idx];
}
```
- `thread_count==0` 时 `Create` 什么都不做，`NextLoop` 返回 baseloop—— 这就是 `SetThreadCount(0)` 单 Reactor 模式的由来。
- round-robin 让新连接均匀分摊到各工作线程，避免负载倾斜。

## 三、为什么每个工作线程都独立跑EventLoop，而不是共享一个？

在传统的多线程模型中，常见的做法是“单epoll监听，多工作线程共享同一个事件”。
每个工作线程都独占一个EventLoop，包含独立的Poller，主要有以下四大核心优势：

#### 1. 彻底避免锁竞争与上下文切换（无锁化/极高吞吐量）

- **共享 Loop 模型**：如果多个线程共享一个 `Poller` 或同一个任务队列，每次有套接字事件就绪，所有线程都要去抢同一个锁来取任务；或者多个线程同时对同一个 `epoll_fd` 调用 `epoll_ctl`，造成严重的**锁竞争（Lock Contention）**。
    
- **独立 Loop 模型**：一个 `Connection` 从出生到销毁，其 Socket 的读、写、协议解析、超时刷新，**100% 绑定在某一个固定工作线程的 EventLoop 内**。该线程处理它手头上的那些连接时**完全不需要加锁**，CPU Cache 命中率极高。
    

#### 2. 避免惊群效应（Thundering Herd Problem）

- 如果多个线程同时对同一个 `epoll_fd` 进行 `epoll_wait`，当一个 Socket 有数据到达时，内核可能会唤醒多个沉睡的线程，但最终只有一个线程能读取到数据，其它线程白白浪费 CPU 上下文切换的开销。
    
- 独立 `EventLoop` 的每个 `Poller` 句柄由独立线程持有，**严格做到“谁的连接谁响应”**，从根本上杜绝了惊群。

#### 3. 避免数据乱序与复杂的并发状态机

如果多个线程同时处理同一个套接字的 I/O 事件：

- 假设 Socket 连续收到了数据包 A 和数据包 B。
    
- 如果共享线程池，**线程 1** 可能在处理包 A，**线程 2** 可能在处理包 B。因为线程调度不确定，极有可能出现 **包 B 比包 A 先处理完** 的业务灾难，应用层必须写非常复杂的锁和序号重组逻辑。
    
- 在独立 `EventLoop` 中，包 A 和包 B 必然在同一个线程中**串行**依次读取，天然保证了消息的 TCP 顺序性。
    

#### 4. 高度可扩展（充分利用多核 CPU）

- 这种架构具有极佳的**水平扩展能力**：如果你有 8 核 CPU，就开 8 个子线程 `LoopThread`。
- 8 个 `EventLoop` 就像 8 个独立的单线程服务器，各自运行在不同的 CPU 核心上，彼此互不干扰，几乎能实现线性级别的性能提升。

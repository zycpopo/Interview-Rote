## 一、传输层（TCP / UDP）

### 0001｜三次握手中序号和确认应答号怎么变？
- **重要程度**：⭐⭐⭐⭐⭐
- **日期**：2026-09-06
- **问题**：TCP 三次握手每一次报文里，序号 seq 和确认应答号 ack 是怎么变化的？
- **我的解答**（要点）：
  - ① 客户端→服务器（SYN=1,ACK=0）：**seq=x**（客户端 ISN 随机），ACK=0 故 ack 无效。作用：宣布"我的坐标原点在 x"。
  - ② 服务器→客户端（SYN=1,ACK=1）：**seq=y**（服务器 ISN 随机），**ack=x+1**。作用：报自己原点 + 确认客户端原点（期待客户端下一个字节 x+1）。
  - ③ 客户端→服务器（ACK=1,SYN=0）：**seq=x+1**，**ack=y+1**。作用：确认服务器原点，双方原点对齐，连接建立。
  - 概念：**seq = 本报文段第一个数据字节的编号**（是相对坐标不是累计计数，原点=ISN；数据量 = 当前 seq − ISN）；**ack = 期待对方下一个字节的序号**（累积确认）。
  - **SYN 占一个序号（虚拟字节）** → 所以 ack 永远是"对方 seq+1"，第三次客户端 seq 顺延为 x+1。
  - 双向坐标系：seq 报自己方向，ack 确认对方方向，两者各说各的。
  - 服务器不会认为要接收 0~x 的字节：握手只是对齐坐标系原点，字节流从 ISN 起算，之前一片空白。
  - ISN 为何随机：防序列号预测攻击（TCP 劫持/注入）+ 避免新旧连接报文序号重叠混淆。
- **状态**：✅已解决
- **记忆锚点**：**"seq 报自己，ack 认对方；ack 永远是对方 seq+1（SYN 占一号）"**。轨迹：①seq=x → ②seq=y,ack=x+1 → ③seq=x+1,ack=y+1。握手=对齐坐标系原点。

### 0002｜旧连接延迟报文为何会污染新连接？seq 会碰巧对上吗？
- **重要程度**：⭐⭐⭐⭐⭐
- **日期**：2026-09-06
- **问题**：（结合时序图）第一次 PUSH,ACK 被网络阻塞，超时重传时服务器断电重启回 RST；第二次用相同四元组重建连接后，旧延迟报文到达被误收造成数据错乱，为什么？两次连接 ISN 不同，seq 还会碰巧对上吗？
- **我的解答**（要点）：
  - **第一次 PUSH 没成功的原因**：原始 PUSH(seq=1,len=10) 被网络阻塞滞留；客户端超时重传同一报文，但此时服务器已断电重启处于 CLOSED，CLOSED 收到非 SYN 报文直接回 RST → 第一次连接断开。
  - **数据错乱的直接原因**：造成错乱的不是重传报文（重传触发了 RST），而是**第一次被网络阻塞、在网络中滞留的原始 PUSH 报文**。第二次连接用相同四元组、ISN 从 0 起（图中简化），新连接服务器期待 seq=1；旧报文 seq=1 恰好落在接收窗口内 → 服务器无法区分新旧连接，当成新连接合法数据接收 → 错乱。
  - **根本原因**：TCP 报文无"连接 ID"，只靠【四元组 + seq 是否在接收窗口内】识别合法性。三条件凑齐即误收：①新旧连接四元组相同；②网络中存在 MSL 内的延迟旧报文；③旧报文 seq 落在新连接接收窗口内。
  - **seq 会碰巧对上吗？会。** 序号空间仅 2^32≈42.9 亿（有限），且接收窗口是连续区间不是一个点，碰撞概率 ≈ 窗口大小/2^32：普通 64KB 窗口约十万分之一；1MB 窗口约万分之二；高速大窗口（1GB）可达约 1/4。
  - **概率放大器**：①高速网络序号快速回绕（10Gbps 约 3.4 秒一圈，MSL 内回绕几十次）；②窗口扩大选项使窗口可达 1GB；③相同四元组快速重连，旧报文未消亡新窗口已移动。
  - **历史教训**：早期 BSD 的 ISN 是基于时间的递增算法（可预测），导致 TCP 劫持攻击；现代 ISN 用密码学安全随机数，但随机只降概率不消除可能。
  - **三层防护**：①**ISN 随机化**——降低新旧序号重叠概率；②**TIME_WAIT(2MSL)**——主动关闭方等旧报文消亡后才允许同四元组重连；③**时间戳 PAWS**——报文带单调递增时间戳，时间戳旧的直接丢弃，从根本上区分新旧报文（终极兜底）。
- **状态**：✅已解决
- **记忆锚点**：**"旧报文迷路，新连接开门，seq 撞进窗口就被收——所以 ISN 随机降概率、TIME_WAIT 等消亡、PAWS 时间戳兜底，三层保险一层比一层硬。"** TCP 不靠"绝对不可能"，靠概率低+等消亡+时间戳叠加把风险压到零。

### 0003｜为什么每次建立 TCP 连接 ISN 都要求不一样？和重传时 seq 不变矛盾吗？
- **重要程度**：⭐⭐⭐⭐⭐
- **日期**：2026-09-07
- **问题**：为什么每次建立 TCP 连接时初始化序列号（ISN）都要求不一样？这和"重传 SYN 时 seq 不变"矛盾吗？
- **我的解答**（要点）：
  - **不矛盾，适用层面不同**：①"重传 seq 不变"指**同一次 connect 尝试内**，连接还没建立成功，重传是把同一个报文再发一遍；②"每次建连 ISN 不一样"指**不同连接实例之间**，一次 connect 失败后重新 connect 才生成新 ISN。
  - 时间线：第1次 connect 生成 ISN=x → 发 SYN(seq=x) → 丢了重传 SYN(seq=x)（同一次尝试内不变）→ 多次失败 connect 超时销毁 → 第2次 connect 生成新 ISN=x' → 发 SYN(seq=x')。
  - **为什么不同连接 ISN 必须不一样**：
    ① **防旧连接延迟报文污染新连接**（关联 0002）：相同四元组重建连接时，若 ISN 相同，旧报文 seq 直接落在新连接接收窗口内被误收 → 数据错乱；ISN 随机不同使新旧序号空间大概率不重叠。
    ② **防 TCP 序列号预测攻击**：ISN 可预测（固定/简单递增）时，攻击者能算出下一个连接的 seq，伪造报文注入连接（劫持/注入/RST 攻击）；现代用密码学安全随机数。
    ③ **区分新旧连接**：四元组可复用（TIME_WAIT 后端口复用），ISN 是区分"新连接还是旧连接残留报文"的关键标识。
  - 两个规则互补：重传保证"同一连接内可靠"，ISN 随机保证"不同连接之间不串台"。
- **状态**：✅已解决
- **记忆锚点**：**"重传不变（同一封信重抄），建连必新（新信新编号）；ISN 随机 = 防旧报文串台 + 防劫持。"**

## 二、应用层（HTTP / HTTPS / DNS）

### 0001｜请求头和响应头是不是都有 Content-Length？
- **重要程度**：⭐⭐⭐⭐
- **日期**：2026-09-05
- **问题**：HTTP 请求报文和响应报文中的请求头/响应头是不是都有 Content-Length？（注意正确拼写是 Content-Length，不是 context-Length）
- **我的解答**（要点）：
  - 不是"都有"，准确说法：**只要有消息体（body）就带，没有 body 就不带**。Content-Length 描述 body 的字节数，作用是让接收方知道"读多少字节算读完、报文是否完整"。
  - 请求报文：POST/PUT 等带 body 的请求 → 有（或用 chunked）；GET/HEAD/DELETE 等不带 body → 没有。
  - 响应报文：正常返回实体的响应 → 有；1xx / 204 No Content / 304 Not Modified → 没有；使用 `Transfer-Encoding: chunked` 分块传输 → 没有（两者互斥，chunked 优先）；HEAD 请求的响应会**带** Content-Length 头但**无 body**（表示"若是 GET 会返回多少字节"）。
  - 关键考点：**Content-Length 与 chunked 互斥**。静态长度已知 → Content-Length；动态/流式长度未知 → chunked（每个分块标长度，末尾 `0` 块收尾）。
  - 进阶：Content-Length 与真实 body 不符会触发 400，HTTP/1.1 下可能被利用做"请求走私"攻击。
- **状态**：✅已解决
- **记忆锚点**：Content-Length = "这顿饭一共几两"；chunked = "边做边上菜，每盘报一次量，最后上盘空的收尾"。一句话：**有 body 才谈长度，长度未知就分块，两者不能同时用**。

### 0002｜强缓存和协商缓存的区别及实现原理？
- **重要程度**：⭐⭐⭐⭐⭐
- **日期**：2026-09-05
- **问题**：HTTP 的强缓存和协商缓存有什么区别？各自的实现原理是啥？
- **我的解答**（要点）：
  - 核心区别：**强缓存没过期就直接用本地缓存、根本不发请求（本地拍板）；协商缓存发请求去问服务器资源变没变（服务器拍板），没变返回 304 空 body 继续用本地缓存，变了返回 200+新资源**。
  - 强缓存字段：`Expires`（HTTP/1.0，绝对时间）/ `Cache-Control: max-age=xx`（HTTP/1.1，相对秒数，优先级高于 Expires）。命中显示 200 (from disk/memory cache)，0 网络请求。
  - 协商缓存两套机制：① `Last-Modified`（响应）↔ `If-Modified-Since`（请求），基于修改时间；② `ETag`（响应）↔ `If-None-Match`（请求），基于内容指纹。`ETag` 优先于 `Last-Modified`（精度、防误判）。
  - 完整流程：**先强缓存（第一道闸）→ 过期后再协商缓存（第二道闸）→ 都没有才完整重新请求**。
  - 加分细节：强缓存适合不常变静态资源+文件名加 hash；Last-Modified 秒级精度、touch 会误判；ETag 在负载均衡多服务器下需统一生成算法，否则缓存频繁失效。
- **状态**：✅已解决
- **记忆锚点**：强缓存 = 直接吃自家冰箱（不去超市）；协商缓存 = 先打电话问超市还新鲜不，新鲜继续吃旧的。口诀：**"强缓存本地拍板，协商缓存问服务器拍板；先强后协，ETag 压过 Last-Modified。"**

### 0003｜HTTPS 建立连接的过程？
- **重要程度**：⭐⭐⭐⭐⭐
- **日期**：2026-09-05
- **问题**：HTTPS 建立连接的过程是怎么样的？
- **我的解答**（要点）：
  - 三段式：**① TCP 三次握手（1.5 RTT）→ ② TLS 握手（TLS1.2 约 2 RTT / TLS1.3 约 1 RTT）→ ③ HTTP 加密通信**。
  - TLS 1.2（RSA 方案）：ClientHello（版本+套件+client_random）→ ServerHello（选套件+server_random）+ 服务器数字证书 → 客户端验证证书（CA 签名链/有效期/域名）→ ClientKeyExchange（客户端生成 premaster，用服务器公钥加密发送）→ 双方用 client_random+server_random+premaster 派生对称会话密钥 → ChangeCipherSpec+Finished → 之后用对称加密（AES）通信。
  - **RSA 方案缺陷**：premaster 直接加密发给服务器，服务器私钥泄露可解密全部历史流量 → 无前向保密。
  - 现代用 **ECDHE**：服务器发临时 ECDHE 公钥（私钥签名防篡改），客户端也生成临时密钥对，双方用 ECDH 各自算出 premaster（**premaster 不出现在网络上**），临时密钥用完即焚 → **前向保密**（长期私钥泄露也不影响历史会话）。
  - **TLS 1.3**：ClientHello 直接带 key_share → 1-RTT；重连 0-RTT（有重放风险，只用于幂等请求）；移除 RSA 交换和老套件。
  - 数字证书作用：防**中间人攻击**，验证三要素 = 签名链有效 + 未过期 + 域名匹配。
  - 为什么混合加密：非对称慢，只用来做"密钥交换+身份认证"；数据正文用对称加密（快）。
- **状态**：✅已解决
- **记忆锚点**：HTTPS = 开门(TCP) → 对暗号(TLS) → 密聊(HTTP over AES)。TLS 1.2 四步口诀：**"你好(Hello)→亮证(证书)→换钥(密钥交换)→开聊(Finished)"**。一句话：**"ECDHE 保前向，TLS1.3 省一圈"**。

### 0004｜TLS 四次握手分别是啥？
- **重要程度**：⭐⭐⭐⭐⭐
- **日期**：2026-09-06
- **问题**：HTTPS 中 TLS 四次握手分别是啥？
- **我的解答**（要点）：
  - 概念澄清：**"四次握手" = 四类握手报文（消息），不是四个来回 = 2 个 RTT**（①和④各是单向消息，分别与②③组成两轮往返）。
  - ① **ClientHello**（客户端→服务器）：支持的 TLS 版本、加密套件列表、随机数 client_random、Session ID。报能力。
  - ② **ServerHello + Certificate**（服务器→客户端）：选定版本+套件、返回 server_random、发数字证书（含公钥，CA 签名）、ServerHelloDone。拍板+亮证；客户端此时自行验证证书（CA 签名链/有效期/域名）。
  - ③ **ClientKeyExchange + ChangeCipherSpec + Finished**（客户端→服务器）：RSA 方案下发送用服务器公钥加密的 premaster；双方用 client_random+server_random+premaster 派生对称会话密钥；客户端发加密 Finished 验证密钥一致。
  - ④ **ChangeCipherSpec + Finished**（服务器→客户端）：服务器切加密模式+加密 Finished 回发，客户端解开比对一致 → 握手完成，之后 HTTP 数据全用对称密钥加密。
  - ECDHE 变体：②多一条 **ServerKeyExchange**（服务器临时 ECDHE 公钥+私钥签名）；③改为发送客户端临时 ECDHE 公钥，双方用 ECDH 各算 premaster，**premaster 不出现在网络上** → 前向保密。
- **状态**：✅已解决
- **记忆锚点**：四次握手 = **"你好(ClientHello) → 亮证(ServerHello+证书) → 换钥(密钥交换) → 开聊(双发 Finished 对表)"**。③④ 的 Finished = 双方拿同一把钥匙互相对表，对得上说明密钥协商成功。

## 三、网络层（IP / 路由）

### 0001｜为什么有 IP 了还需要 MAC 地址？
- **重要程度**：⭐⭐⭐⭐⭐
- **日期**：2026-09-05
- **问题**：网络层用 IP 就能把数据送到主机，为什么还需要 MAC 地址？
- **我的解答**（要点）：
  - IP 负责"从源到目的"的端到端逻辑寻址（跨网络），MAC 负责"每一跳"的局域网内物理投递，两者管的不是一回事。
  - 关键事实：跨网络转发时 **IP 全程不变，MAC 每一跳都换**（源主机→网关→路由器→…→目的主机，每跳重写帧头的源/目的 MAC，IP 头不动）。
  - 为什么不能用 IP 替代 MAC：① 底层链路异构（以太网/WiFi/光纤各有自己的物理寻址），IP 是架在所有链路之上的通用逻辑地址；② 同一子网内 IP 的网络号相同，无法用 IP 在局域网内唯一标识具体设备；③ 网卡/交换机等硬件只认 MAC，不解析 IP；④ 分层解耦：网络层不管底层介质，链路层不理解"互联网"，各自独立演进。
- **状态**：✅已解决
- **记忆锚点**：IP 是快递面单上的收件地址（全程跟着包裹走），MAC 是每段路上司机之间的交接签收（到一站换一个交接人）。口诀：**"IP 管全程，MAC 管一跳"**。ARP = 已知对端 IP、求对端 MAC。

## 1. C++内存分区，堆和栈的区别

C++进程的内存从低地址到高地址分别由这几个部分组成:
- 代码段：（.text）存放机器指令，只读。
- 数据段：（.data）已经初始化的全局变量和静态变量。
- BSS段：未初始化的全局变量和静态变量。
- 堆：向上生长，需要我们手动管理（new/delete），空间大但效率低。
- 栈：向下生长，编译器自动管理，空间小但效率极高。

**六个角度对比堆和栈：**
1. 管理方式：栈由编译器自动分配和释放（函数进入时压栈，返回时弹出）；但是堆需要由我们手动管理，忘记释放就会内存泄漏。
2. 空间大小：栈空间很小（Linux默认8MB,Windows默认1MB），超出就栈溢出。堆空间很大，32位系统理论上可达数GB，几乎不受限制。
3. 碎片问题：栈不会产生碎片，因为严格的后进先出，内存总是连续释放。堆频繁操作new或者delete就会产生碎片，中间释放的小块可能无法被大块请求利用。
4. 生长方向：栈是向低地址生长，从高往低压。堆向高地址生长（从低往高分配）。两者是相向而行，中间是可用空间。
5. 分配效率：栈分配只需移动栈指针，一个指令直接修改栈指针寄存器，特别块。堆分配需要在空间链表中搜索合适大小的块，还可能触发系统调用扩展内存，会慢很多。
6. 线程安全：每个线程有自己独立的栈，天然线程安全。堆是所有线程共享的，多线程同时new/delete需要加锁，这也同样是影响分配效率的原因之一。

**常见的问题：**
- **栈溢出是什么？** 栈的空间不是很大，所以如果一个程序递归太深，导致每次调用函数都要压栈，或者就是在栈上开了一个巨大的数组或者其他变量，就会直接超出栈的空间限制，触发栈溢出，操作系统会直接发送SIGSEGV信号中止进程。
- **堆上的对象和栈上的对象有什么区别差异？** 生命周期不同：栈对象在作用域结束后自动析构，堆对象必须手动delete才能析构。还有堆对象的地址在整个生命周期内不变，适合被指针引用；栈对象的地址在函数返回后失效，不能返回局部变量的指针。拷贝的语义不同，栈对象赋值时值拷贝，堆对象通常通过指针传递，避免拷贝开销。
- **实际开发中怎么管理内存？** 现代c++尽量不手动管理内存。使用智能指针，自动管理生命周期；用智能指针（unique_ptr、shared_ptr）自动管理生命周期；用容器（vector、string）代替手动数组；遵循 RAII 原则——资源在构造时获取，在析构时释放。如果性能敏感（比如游戏引擎、高频交易），可以用内存池预分配一大块堆内存，避免频繁的系统调用和碎片。

## 2. new和malloc的区别是什么？

1）new是C++运算符，以new myclass（10）举例，这一行代码，编译器实际上拆分两件事。
First：调用operator new(sizeof(myclass))分配内存，这个函数内部实现其实就是调用malloc；
second：在分配的地址上调用myclass的构造函数初始化对象。
new返回的具体类型的指针，mallock返回的是void* 需要强转，new失败抛bad_alloc异常，而malloc失败返回NULL。
所以 new 的完整调用链路是：`new` → `operator new` → `malloc` → `mmap`/`brk`（操作系统底层）。

2）malloc是C标准库函数，只负责分配一块指定大小的堆内存，不调用任何构造函数。malloc(sizeof(myclass))只做了一件事，就是向操作系统申请一块指定大小的原始内存，返回的是void* 指针。这块内存里面存的还是垃圾值，没有任何初始化

3）其他的关键差异包括但不限于：new不需要手动计算大小，编译器会自动计算sizeof，而malloc必须手动传大小参数。new可以被类重载，malloc不能。new[ ]分配数组会额外记录元素个数，delete[ ]根据这个数字批量调用析构；

4）常见问题：

1. **new底层一定调malloc？**
不一定，operator默认是调用malloc。但是如果你重载operator用自己的分配器（比如从内存池分布）。标准只要求operator new返回一块足够大的对齐内存，不规定底层实现。

2. **delete[] 为什么不能用 delete 替代？**
 `new[]` 分配数组时，编译器会在内存块头部多分配几个字节记录元素个数 N。`delete[]` 读取这个 N，然后循环调用 N 次析构函数，最后释放整块内存。如果用 `delete` 代替，它只调用一次析构（第一个元素），剩下 N-1 个元素的析构函数不会被调用，资源泄漏。对于 POD 类型（没有析构函数）混用不会崩溃，但属于未定义行为，不要这么做。

## 3. free和delete区别的是什么？

1）free是C语言函数，配合使用malloc使用。只把一件事给内存系统，不关心内存里面的是什么，不调用任何析构函数。delete是C++运算符，配合new使用，首先先调用对象的析构函数，释放内部管理的资源，再释放对象本身占的内存。

2）delete本质上跟new是反过来的，也是两步，首先是调用对象的析构函数，第二步调用operator delete（myclass）释放内存，这个的默认底层实现就是调用free。所以delete = 析构+free。

3）free的底层实现，首先会找到对象前面的metadata（malloc分配内存时偷偷加的头部，记录这块内存的大小），标记已释放，然后尝试和相邻的空闲块合并（减少碎片）。如果这块内存很大，直接munmap还给内核，否则放入空闲链表，等下次malloc复用。

4）**现代C++还需要手动new/delete吗？** 答案是尽量不要。现代C++推荐使用智能指针管理堆内存，用容器管理动态数组。手动new或者delete很容易导致内存泄漏或者重复释放，智能指针通过RAII自动管理生命周期，从根本上避免这些问题。

## 4. placement new的作用

**作用：**
Placement new 只做一件事——在你给定的内存地址上调用构造函数，不分配任何内存。语法是 `new (ptr) Type(args)`，其中 `ptr` 是一块已经分配好的内存。对应地，销毁时不能用 `delete`（它会试图释放这块内存，但这块内存不是 `new` 分配的），必须手动调析构函数 `obj->~Type()`，然后用原始方式释放内存。

**为什么不能用 delete 释放**
`delete obj` 做两件事：调析构函数 + 调 `operator delete` 释放内存。但 placement new 构造的对象，其内存可能来自栈上的 `char` 数组、内存池、共享内存段——这些都不是堆分配器管理的。如果对这种内存调 `operator delete`，行为是未定义的（通常直接崩溃）。正确做法：先手动调析构 `obj->~MyClass()`，再用原始方式释放内存（栈上的自动回收，内存池的还给池，`new char[]` 分配的用 `delete[]` 释放）。

**内存对齐要求**
placement new 要求你提供的内存地址满足目标类型的对齐要求（`alignof(Type)`）。如果用 `char` 数组做缓冲区，必须加 `alignas(Type)` 保证对齐，否则在某些架构上会触发硬件异常或性能严重下降。C++17 的 `std::aligned_storage` 或直接用 `alignas` 都能解决。

**标准库哪些地方用了 placement new**
`std::vector` 扩容时：分配新的更大内存块，然后用 placement new 在新内存上移动构造旧元素。`std::optional`：内部有一块 `aligned_storage`，有值时用 placement new 构造，无值时调析构销毁。`std::variant`：在同一块内存上构造不同类型的对象。所有内存池/对象池的实现都依赖 placement new。

**常见问题：**
- **为什么不能用 memcpy 代替 placement new？**`memcpy` 只是逐字节拷贝，不调用构造函数。对于有虚函数的类，虚函数表指针不会被正确设置；对于持有资源的类（`string`、`vector` 成员），内部指针会指向错误的地址。只有 POD 类型（没有构造函数、没有虚函数）才能用 memcpy，其他类型必须用 placement new。
- **placement new 会失败吗？** 不会。标准的 placement `operator new` 标记了 `noexcept`，它只是返回你传入的指针，不做任何可能失败的操作。但构造函数本身可能抛异常——如果构造函数抛了，对象没有被成功构造，你不需要调析构函数，但内存仍然需要按原始方式释放。
- **能在同一块内存上反复构造不同对象吗？** 能，这正是 placement new 的典型用法。先调析构销毁旧对象，再用 placement new 构造新对象。`std::variant` 切换类型时就是这么做的。但要注意：新对象的大小和对齐要求不能超过这块内存的容量。
- **placement new 和内存池是什么关系？** 内存池的核心思想是"预分配一大块内存，按需切割使用"。切割出来的小块内存上构造对象就靠 placement new，销毁对象就靠手动调析构。这样避免了频繁调 malloc/free 的开销和内存碎片问题。游戏引擎、数据库、高频交易系统都大量使用这种模式。

## 5. 什么是内存泄漏？什么是野指针？什么是内存越界？如何避免？

**内存泄漏**
- 程序通过new或者malloc在堆上申请了内存，但后来指针被覆盖、函数返回、或者异常跳出，导致这块内存的地址丢了，再也没办法释放。短期看程序不会崩溃，但长期运行，内存会被慢慢吃光，最终分配失败或系统OOM杀进程。
- 避免方法：C++为了避免内存泄漏的问题，就引出了RAII——智能指针管理堆内存，离开作用域自动释放；手动管理时确保每条路径包括异常路径都有对应的delete或者free。

**野指针**
- 指针本身存在，但是指针指向的地址已经被释放了。这时候通过指针读写，行为是未定义的，可能旧数据还在，也有可能读到垃圾值，也可能直接SIGSEGV崩溃。最危险的是看起来很正常，程序结果没问题，bug一直潜伏着。
- 避免方法：delete后立即把指针置为nullptr；不要返回局部变量的地址，用智能指针代替裸指针，析构后自动失效。

**内存越界**
- 访问数组下标超过数组大小范围，或者往malloc（10）分配得10字节之外写数据。越界写入可能覆盖相邻变量，堆管理元数据，甚至函数返回地址，是缓冲区溢出攻击的根源。还有比较常见的场景：C风格字符串未加斜杠零；结构体填充对齐；多线程共享内存。
- 避免方法：在代码层面：统一使用迭代器；明确指定容量；可以使用C++20安全边界库进行测试。编译时开 `-fsanitize=address` 检测越界；循环中严格检查下标范围。

**常见问题**
- **内存越界和堆溢出？** 堆溢出是内存越界的一种特殊情况，往堆上分配的缓冲区之外写数据。栈上数组越界叫栈缓冲区溢出。两者都是越界写入，但攻击面不同：栈溢出可以覆盖返回地址劫持控制流，堆溢出可以覆盖堆元数据或相邻对象的 vtable。
- **泄漏为什么不会立即崩溃？** 因为泄漏可能还没影响程序。泄漏只是内存没释放，程序本身没有错误。操作系统的虚拟内存机制让进程可以持续申请，直到地址空间或物理空间耗尽。长期运行的服务（如web服务器）对泄漏特别敏感，可能跑几天才OOM。

## 6. 内存碎片与内存溢出

**内存碎片**
内存碎片分为两种：外部碎片和内部碎片。
- 外部碎片：频繁分配释放不同大小的内存块后，空闲内存被切成很多不连续的小块。单个小块都不够大，但加起来总量足够。在C/C++中特别严重，因为指针直接指向内存地址，没法像Java那样做内存压缩（移动对象更新所有指针）。
- 内部碎片：分配器按固定粒度分配（比如8字节对齐），你要5字节它只能给你8字节，多出来的三个字节就没用浪费了。内存池也有这个问题，池子里的内存块大小固定，小请求浪费空间。
**内存溢出**

**栈溢出 vs 堆溢出**

|维度|栈溢出 (Stack Overflow)|堆溢出 (Heap Overflow)|
|---|---|---|
|发生区域|栈内存（向低地址增长）|堆内存（动态分配区）|
|根本原因|空间耗尽：递归过深或局部变量过大，超出栈容量|越界写入：往 `malloc`/`new` 分配的块之外写数据|
|触发方式|通常是编程错误（无限递归、栈上大数组）|可以是无意错误，也常是恶意攻击手段|
|后果|程序立即崩溃（SIGSEGV），确定性行为|可能立即崩溃，也可能潜伏——覆盖了什么决定后果|
|安全影响|影响可用性（程序挂了）|影响安全性（可能被利用执行任意代码）|
**常见问题**
- **外部碎片为什么比内部碎片难解决？** 内部碎片是"已知的浪费"，上限可控——选合适的分配粒度或内存池块大小就行。外部碎片是"全局的混乱"，取决于分配释放的随机序列，没法预测。解决它要做内存压缩（移动已分配块来合并空闲块），但 C/C++ 里指针是裸地址，移动了对象就得更新所有指向它的指针，几乎不可能。所以只能靠好的分配策略（best-fit、buddy system）来缓解。
- **堆溢出为什么是严重的安全问题？** 堆溢出让攻击者能覆盖堆里相邻的数据。精心构造溢出内容可以：覆盖函数指针让它指向恶意代码、覆盖对象的 vtable 控制执行流、修改相邻数据改变程序逻辑。配合 ROP 链，即使开了 DEP/NX 保护也能执行任意代码。
- **如何避免栈溢出？** 把递归改迭代；不在栈上放大数组（改用堆分配）；给递归设深度上限；编译时开 `-fstack-protector` 检测。
- **所有递归都会栈溢出吗？** 不会。只要深度在栈容量内就没事。遍历深度 1000 的二叉树没问题（栈深度≈树高），但用递归遍历百万节点链表就会溢出（栈深度≈节点数）。尾递归可以被编译器优化成循环，不增长栈空间。

## 7. 如何避免内存碎片

内存碎片分两种：
- **外部碎片**：空闲内存总和够用，但分散在不连续的小块中，无法满足大分配请求
- **内部碎片**：分配的内存块比实际请求大，多出来的部分浪费了

避免策略需要从多个层面系统考虑：
- **减少动态内存分配**：最好的避免就是不做。优先用栈内存、静态存储期对象或成员变量，栈分配速度快且无碎片。
- **使用STL容器管理连续内存**：`std::vector`、`std::string`、`std::array` 在内部管理一块连续的动态增长内存，保证元素内存连续，极大减少外部碎片。如果提前知道大致大小，用 `reserve()` 预分配容量，避免多次扩容带来的碎片。
- **智能指针防止泄漏**：`std::unique_ptr`、`std::shared_ptr` 通过 RAII 自动管理生命周期，防止忘记释放导致的”永久碎片”。对碎片的作用是间接的，但很关键。
- **对象池（Object Pool）**：对于频繁申请释放的固定大小小对象（链表节点、网络数据包等），对象池是终极方案：一次性分配一大块内存，内部维护空闲链表，分配和归还都是 O(1) 操作，完全避免外部碎片。
- **自定义分配器(Custom Allocator)**：STL容器支持自定义分配器，可以实现基于内存池的分配器替换默认 `new/delete`，为特定类型对象提供无碎片的分配策略。
总结一下：**从”能不分配就不分配”到”分配了就连续分配”再到”自己管理分配”，层层递进。**

**常见问题**
- **外部碎片和内部碎片能举例说明吗？** 外部碎片：堆上零散分布着 A、B、C 三个对象，中间有空隙，总空闲够分配 D，但没有一块连续空间放得下。内部碎片：malloc 为了内存对齐多给了几个字节，或者对象池块大小固定但你申请的对象比块小。
- **std::list 和 std::vector 在碎片上有什么不同？** vector 是单块连续内存，无外部碎片，扩容时可能产生暂时碎片。list 每个节点独立分配，频繁插入删除会产生大量外部碎片，高频场景应避免用 list。
- **智能指针怎么帮助减少碎片？** 主要贡献是防泄漏。泄漏的内存对系统来说就是永远无法使用的碎片，智能指针确保内存能被正确释放，间接对抗了泄漏引起的碎片。
- **线程安全的对象池怎么设计？** 最简单的方式是 mutex 保护 freeList。高性能场景用线程本地存储（TLS），每个线程有自己的空闲列表，避免锁竞争。本线程池耗尽时再去访问全局加锁的池子。
